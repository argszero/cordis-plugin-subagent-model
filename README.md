# @argszero/cordis-plugin-subagent-model

Live model selection for dsh subagents — see which model a delegation runs on,
and give it one of its own.

Source: [discussion #7116](https://github.com/deepseek-ai/deepseek-harness/discussions/7116)
("Clearly show the subagent model and let user change it on the fly").

## The gap

A delegation inherits its parent's route. `resolveChildAgentOptions` copies the
parent's latest request header into the child's `AgentOptions`, and the only
per-child lever is `agentOptions` at delegation time, so:

- a subagent always runs on the model the parent currently uses, and
- once a child is running, its route is fixed for the whole run.

Nothing displays the child's route either. The durable request header records it
per request, but the transcript a user reads does not carry it.

Both halves of the report are the same missing seam from two sides.

## What this plugin does

Mounted on the public `agent/request` waterfall, it rewrites the resolved config
of every **in-process subagent** request (any Agent whose delegation depth is at
least one) to a plugin-owned selection:

- **A route of its own** — `provider`, `model` and/or `reasoningEffort` are
  resolved per request rather than per run, so a selection changed at runtime
  takes effect on a **running** child's next step. A field the selection leaves
  unset keeps the inherited value, so `{ model }` alone re-points the model
  inside the parent's provider.
- **A switch you can reach** — the `subagent_model` tool (`get` / `set`) reads
  and writes that selection from the agent you are already talking to. Writing
  is allowed only for a top-level agent: the selection is deployment-wide for
  subagents, so a child silently re-routing its siblings is not a privilege the
  report asked for.
- **A visible route** — for each child transcript, one durable notice states the
  route that child runs on, and a later route change states the boundary
  (`assistant turns above this point were generated by …; the session continues
  with …`). Notices are ordinary session events, so they survive resume. Set
  `announce: false` to route silently.

A route change that names no reasoning effort **clears** the inherited effort,
mirroring `resolveChildAgentOptions`: the effort belonged to the route that
carried it, so the newly selected model resolves its own default instead of
inheriting a level its adapter may not offer.

## Install

```sh
dsh plugin add @argszero/cordis-plugin-subagent-model
```

Mount it the way any bundle patch is mounted (`dsh.bundle.patch` →
`cordis.patch.yml`), or add the row by hand:

```yaml
- insert:
    - id: subagent-model
      name: '@argszero/cordis-plugin-subagent-model'
```

With no config the plugin only observes: nothing is re-routed, and the sole
effect is the per-child route notice. To pre-select a route in the profile:

```yaml
- set:
    - id: subagent-model
      config:
        provider: deepseek
        model: deepseek-chat
        reasoningEffort: high
        toolName: subagent_model
        announce: true
```

## Using it

Ask the agent you are talking to, or call the tool directly:

```jsonc
// what will subagents run on?
{ "action": "get" }

// give every subagent a route of its own (running children follow from their next step)
{ "action": "set", "provider": "deepseek", "model": "deepseek-reasoner" }

// back to inheritance
{ "action": "set", "clear": true }
```

The result is structured:

```jsonc
{
  "action": "set",
  "role": "root agent",          // or "subagent"
  // exactly the fields the selection names, so a model-only override does not
  // pretend to name a provider; "none" = subagents inherit
  "selection": "provider=deepseek model=deepseek-reasoner",
  "route": "deepseek/deepseek-reasoner",   // what THIS agent's next request uses
  "source": "selection"          // "selection" | "inherited" | "unset"
}
```

`route` reports a field the agent does not carry as `inherited`, never as a
guess: a half-specified override cannot read as an unknown provider.

## Boundaries (stated, not implied)

- **In-process children only.** `spawn`, `fork` and continuation providers run
  the child here and cross this waterfall. An out-of-process child
  (`subagent-codex`, `subagent-acp`, `subagent-claude-code`, `subagent-dsh-sdk`)
  has no `agent/request` in this process; its route is untouched by
  construction. The plugin does not pretend to reach it.
- **One selection for all subagents.** Per-child targeting is deliberately not
  in v0.1.0; the report asks for a subagent route, not for a per-child roster.
- **`get` on a root agent reports the selection, not the root's own route.** The
  root's model belongs to the harness model-selection surface, not to this
  plugin.
- **The notice is a real user-role session event.** It is visible to the child
  model as well as to the user; that is what makes it durable and resumable.
  `announce: false` removes it.
- **A denial of the tool's `set` from a subagent is an error, not a silent
  no-op**, so the delegating agent learns why.

## Compatibility

Harness packages are **peers**, never dependencies: a nested copy of the runtime
is the failure mode of every plugin that gets this wrong.

```
@deepseek-ai/cordis        ^4.0.2
@deepseek-ai/dsh-agent     >=0.1.2-rc.1 <0.2.0 || >=0.1.3-alpha.2 <0.2.0 || >=0.1.5-alpha.1 <0.2.0 || >=0.1.6-alpha.1 <0.2.0
@deepseek-ai/dsh-llm       >=0.1.2-rc.1 <0.2.0 || >=0.1.3-alpha.2 <0.2.0 || >=0.1.5-alpha.1 <0.2.0 || >=0.1.6-alpha.1 <0.2.0
@deepseek-ai/dsh-session   >=0.1.2-rc.1 <0.2.0 || >=0.1.3-alpha.2 <0.2.0 || >=0.1.5-alpha.1 <0.2.0 || >=0.1.6-alpha.1 <0.2.0
@deepseek-ai/dsh-subagent  >=0.1.2-rc.1 <0.2.0 || >=0.1.3-alpha.2 <0.2.0 || >=0.1.5-alpha.1 <0.2.0 || >=0.1.6-alpha.1 <0.2.0
@deepseek-ai/dsh-tools     >=0.1.2-rc.1 <0.2.0 || >=0.1.3-alpha.2 <0.2.0 || >=0.1.5-alpha.1 <0.2.0 || >=0.1.6-alpha.1 <0.2.0 || >=0.2.1-rc.1 <0.2.1
```

A prerelease range only admits its own version tuple, so each supported line is
named explicitly; an unsupported line fails loudly at install time instead of
silently loading a second copy of the harness runtime.

Every admitted version was probed, not assumed: the suite runs in a clean
project per line against the published packages, with the resolved versions
checked before the tests execute (`scripts/probe-lines.mjs`).

| dsh line | versions probed | result |
|----------|-----------------|--------|
| 0.1.2 | `0.1.2-rc.1` | 24/24 |
| 0.1.3 | `0.1.3-alpha.2` | 24/24 |
| 0.1.5 | `0.1.5-alpha.1`, `0.1.5-alpha.2`, `0.1.5-rc.1`, `0.1.5-rc.2` | 24/24 |
| 0.1.6 | `0.1.6-alpha.1`, `0.1.6-alpha.2` | 24/24 |
| 0.2.1 | `0.2.1-rc.1`, `0.2.1-rc.2`, `0.2.1-rc.3` | 45/45 |

The probe installs with `--legacy-peer-deps` because it pins a subset of the
harness (the rest floats to the newest patch of the same line, and an alpha's
own peer on a sibling package is then unresolvable); the five packages this
plugin imports are asserted to be exactly the probed version before the suite
runs, so the pin cannot silently drift.

## Tests

```sh
npm test
```

The suite runs against a real `@deepseek-ai/cordis` context (real plugin
injection, real waterfall dispatch) and the real `@deepseek-ai/dsh-tools`
schema validation, driving the registered handlers with Agent-like subjects. The
decisive observation in every case is the value that leaves the handler — the
config the agent loop would dispatch to the provider.
